    Escenarios de referencia¶

    [!NOTE] 🛠️ Página generada por MkDocs; cada bloque se incrusta en vivo desde examples/. Copia el escenario que más se acerque y cambia project.name.

    En esta página: 01 Default core · 02 Mínimo · 03 Rutas custom · 04 Pack de stack · 05 Fusiones MVP · 06 Agentes desacoplados · 07 Pack frontend · 08 Completo · Relacionado

    01 — Default core (recomendado)¶

    Solo método, 3 activos, stubs del core, sin pack ni fusiones extra.

    # Recomendado en v0.3: núcleo sin pack ni fusiones extra.
# Uso: primer proyecto SDAF, o laboratorio de método. Tres activos evitan thrash.
# Materializar AGENTS.md con project.name; Gate 0 usa src/ y tests/ por defecto.
# Qué no hace: no añade Frontend ni skills de un lenguaje.

sdaf:
  version: "0.3.0"

project:
  name: MiProyecto
  language: es

stack:
  pack: null
  src_path: src
  tests_path: tests

agents:
  active:
    - specification
    - architecture
    - testing-review
  stubs:
    - product
    - domain
    - application
    - devops
    - review
    - testing
  fusions: {}

    02 — Mínimo¶

    Mínimo obligatorio (defaults de rutas).

    # Mínimo válido: mismas reglas que 01, YAML corto.
# Uso: bootstrap rápido. src_path y tests_path se omiten → default src y tests.
# fusions omitido → equivalente a {}.
# No omitir sdaf.version, project.*, stack.pack ni agents.active/stubs.

sdaf:
  version: "0.3.0"

project:
  name: MiProyecto
  language: es

stack:
  pack: null

agents:
  active:
    - specification
    - architecture
    - testing-review
  stubs:
    - product
    - domain
    - application
    - devops
    - review
    - testing

    03 — Rutas custom¶

    Código/tests fuera de src/ y tests/.

    # Rutas de código/tests no canónicas.
# Uso: monorepo, repo con apps/, backend/, packages/.
# Gate 0 y Testing+Review miran stack.src_path y stack.tests_path, no "src/" a ciegas.
# El árbol SDAF (specs/, worklogs/, handbook) sigue en la raíz; solo cambia el código.

sdaf:
  version: "0.3.0"

project:
  name: MiProyecto
  language: es

stack:
  pack: null
  src_path: apps/api
  tests_path: apps/api/tests

agents:
  active:
    - specification
    - architecture
    - testing-review
  stubs:
    - product
    - domain
    - application
    - devops
    - review
    - testing
  fusions: {}

    04 — Pack de stack¶

    Overlay técnico (stack.pack) sin cambiar el modelo de agentes del core.

    # Pack de stack sin cambiar el modelo de agentes del core.
# Uso: quieres playbooks técnicos (coding standards, slice de API, runtime local)
# pero la implementación la hacen humanos u otros agentes aún stub.
# El pack NO sustituye ADRs de stack: sigue haciendo falta ADR si cambias runtime.
# Pack de referencia: sdaf-stack-dotnet@0.1.1

sdaf:
  version: "0.3.0"

project:
  name: MiProyecto
  language: es

stack:
  pack: sdaf-stack-dotnet@0.1.1
  src_path: src
  tests_path: tests

agents:
  active:
    - specification
    - architecture
    - testing-review
  stubs:
    - product
    - domain
    - application
    - devops
    - review
    - testing
  fusions: {}

    05 — Fusiones MVP¶

    testing-review y domain-application como fusiones explícitas.

    # Fusiones MVP: un agente cubre varios roles (menos handoffs, más contexto por agente).
# Uso: un supervisor humano; misma idea que el modelo de 5 activos de producto
# (Specification, Architecture, Domain+Application, Frontend opcional, Testing+Review).
# Aquí Frontend no está: solo se fusiona implementación de dominio+aplicación.
# testing y review / domain y application quedan stub para desfusionar después.
# domain-application es id de extensión: requiere contratos en el consumidor o pack.

sdaf:
  version: "0.3.0"

project:
  name: MiProyecto
  language: es

stack:
  pack: sdaf-stack-dotnet@0.1.1
  src_path: src
  tests_path: tests

agents:
  active:
    - specification
    - architecture
    - domain-application
    - testing-review
  stubs:
    - product
    - domain
    - application
    - devops
    - review
    - testing
  fusions:
    testing-review: [testing, review]
    domain-application: [domain, application]

    06 — Agentes desacoplados¶

    Testing y Review separados; Domain y Application activos.

    # Agentes desacoplados: sin fusiones. Más handoffs, roles más estrechos.
# Uso: post-MVP, o varios humanos/agentes en paralelo sin pisar archivos.
# testing y review son activos distintos (el core envía ambos como stub; aquí se activan).
# No incluir testing-review en active (sería un tercer dueño de tests/review).
# domain y application activos por separado: el router elige por tipo de salida (modelo vs slice).

sdaf:
  version: "0.3.0"

project:
  name: MiProyecto
  language: es

stack:
  pack: null
  src_path: src
  tests_path: tests

agents:
  active:
    - specification
    - architecture
    - domain
    - application
    - testing
    - review
  stubs:
    - product
    - devops
  fusions: {}

    07 — Pack frontend¶

    Pack + agente frontend (extensión; el core no lo envía).

    # Pack + agente Frontend (extensión). El core no incluye contrato frontend.
# Uso: hay UI y el pack (o el consumidor) aporta agents/frontend-agent.md y su prompt.
# El framework concreto (web, móvil, etc.) lo fija un ADR del consumidor, no esta config.
# infrastructure y ai siguen stub: no se invocan en el handoff canónico.
# Handoff típico: Specification → Architecture → domain-application → frontend
#                                                      ↘ testing-review ↗

sdaf:
  version: "0.3.0"

project:
  name: MiProyecto
  language: es

stack:
  pack: sdaf-stack-dotnet@0.1.1
  src_path: src
  tests_path: tests

agents:
  active:
    - specification
    - architecture
    - domain-application
    - frontend
    - testing-review
  stubs:
    - product
    - domain
    - application
    - infrastructure
    - devops
    - review
    - testing
    - ai
  fusions:
    testing-review: [testing, review]
    domain-application: [domain, application]

    08 — Completo¶

    Todas las claves rellenadas a la vez (referencia de techo).

    # Techo v0.3: todas las claves del esquema, explícitas.
# Uso: plantilla de auditoría o para no depender de defaults. No es el default recomendado
# (muchos activos + pack + fusiones + rutas custom = más superficie de handoff).
# Combina: version, name, language, pack, src_path, tests_path, active, stubs, fusions.
# Ids de extensión (frontend, infrastructure, ai, domain-application) exigen pack o contratos locales.

sdaf:
  version: "0.3.0"

project:
  name: MiProyecto
  language: es

stack:
  pack: sdaf-stack-dotnet@0.1.1
  src_path: apps/web
  tests_path: tests/acceptance

agents:
  active:
    - specification
    - architecture
    - domain-application
    - frontend
    - testing-review
  stubs:
    - product
    - domain
    - application
    - infrastructure
    - devops
    - review
    - testing
    - ai
  fusions:
    testing-review: [testing, review]
    domain-application: [domain, application]
